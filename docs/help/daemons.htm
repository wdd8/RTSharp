There are three different torrent daemons that RT# can control but one important notion to understand is that RT# never talks to these daemons directly, everything goes through RTSharp.Daemon:

RT# application  <-- encrypted gRPC (certificates) -->  RTSharp.Daemon  <-- local -->  torrent daemon

RTSharp.Daemon is a service that runs on the same Linux server as your torrent daemons. It works around various inefficiencies of these daemons (for example by sending only the changes of the listing), it performs the file operations on the torrent data and it supplements some additional features such as the mediainfo, the transfers between servers and the scripts. One RTSharp.Daemon can serve several torrent daemons of different types at the same time.

On the application side, each torrent daemon is handled by a "data provider", which is a plugin. You can have as many data provider instances as you want, for example two rtorrent and one qBittorrent on the same server.

1. rtorrent:

RT# connects to rtorrent with its XML-RPC interface over SCGI. rtorrent does not support delta listing changes, so the daemon has to poll the full listing and compute the changes itself. This requires more resources to sustain fast updates for large lists of torrents.

2. qBittorrent:

RT# connects to the WebUI API of qBittorrent, with an API key or with a username and a password. qBittorrent has its own delta API which is used for the listing. This is the only daemon that accepts V2-only torrents.

3. Transmission:

RT# connects to the RPC interface of Transmission with a username and a password. Transmission also has native delta changes.
