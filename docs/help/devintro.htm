This chapter is for the developers who want to write their own plugins. A plugin is a .NET 10 class library that RT# loads at runtime, it can use everything that the plugin contracts offer: the torrents, the menus of the main window, the servers and their scripts, and much more. The complete list of these contracts is given in the "Plugin API reference" which is generated automatically from the source code.

1. The assemblies:

There are two assemblies that a plugin references:

RTSharp.Shared.Abstractions: The headless contracts, such as IPlugin, Torrent, IDataProvider, IDaemonService, IScript...
RTSharp.Shared.Abstractions.Client: The contracts related to the user interface, such as IPluginHost, BasePlugin, VmWindow...

RT# is built with Avalonia, so the windows of a plugin are Avalonia windows.

2. The project:

The project of a plugin must enable the dynamic loading and declare its version, then import plugin.targets which removes the redundant files from the build output:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <EnableDynamicLoading>true</EnableDynamicLoading>
    <RTSharpPluginVersion>0.0.1</RTSharpPluginVersion>
  </PropertyGroup>

  <ItemGroup>
    <ProjectReference Include="..\..\RTSharp.Shared.Abstractions\RTSharp.Shared.Abstractions.csproj" />
    <ProjectReference Include="..\..\RTSharp.Shared.Abstractions.Client\RTSharp.Shared.Abstractions.Client.csproj" />
  </ItemGroup>

  <ItemGroup>
    <None Update="manifest.json" CopyToOutputDirectory="PreserveNewest" />
  </ItemGroup>

  <Import Project="..\..\plugin.targets" />
</Project>

If the plugin needs to access the internals of RT# itself (for example RTSharp.Models.Torrent in a cell hook), set RTSharpPluginReferencesHost to true and reference the RTSharp project. Be careful: this kind of access can break with any new version of RT#.

3. The manifest:

Each plugin is located in its own folder inside the "plugins" folder of RT#, together with a manifest.json file:

{
    "Module": "MyCompany.MyPlugin.dll",
    "Description": "Does something very useful"
}

Data providers also add "Type": "DATA_PROVIDER", this way RT# knows that it must ask a server and a data provider name when you configure them.

4. The configuration file:

Each instance of a plugin has its own configuration file in the "plugins" folder of the configuration folder. The "Plugin" section is managed by RT# (path of the module, name and id of the instance, and for data providers the server, the data provider name and the color), the other settings at the root of the file belong to the plugin:

{
  "Plugin": {
    "Path": "MyPlugin/MyCompany.MyPlugin.dll",
    "Name": "My plugin",
    "InstanceId": "6c3f4a4e-...."
  },
  "MySetting": 42
}

The plugin describes its own settings with a class deriving from PluginConfigContainer<PluginInstanceConfig> (or PluginConfigContainer<DataProviderInstanceConfig> for a data provider), RT# reads the file into this class and gives it to the plugin through Host.Config. To save the settings, call Host.SavePluginConfig.

5. Loading:

At startup, RT# reads all the configuration files, loads each module in its own load context, then calls ConfigureServices and Init on each plugin. If Init fails, RT# displays the error and continues with the other plugins. When RT# exits, it calls Unload. A plugin must declare the major version of RT# it has been made for in CompatibleMajorVersion.
